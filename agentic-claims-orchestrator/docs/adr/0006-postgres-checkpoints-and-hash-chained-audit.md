# ADR-0006: PostgreSQL for checkpoints, approvals and a hash-chained, append-only audit trail

- Status: Accepted
- Date: 2026-10-17

## Context

Regulators and internal audit require a complete, tamper-evident record of how each claim was handled: inputs (minus PII), every agent step, tool call, model version, policy version, human decision and final outcome. The same data powers crash recovery.

## Decision

- **PostgreSQL 18** via **Drizzle ORM** (typed schema in TS, SQL migrations generated by drizzle-kit and committed; applied at startup or by the Helm pre-upgrade Job).
- Tables: `runs` (current state, optimistic `version`, lease columns), `checkpoints` (state snapshot after every step), `audit_events`, `approvals`, `pii_vault`.
- Every state transition is **one transaction** with `SELECT ... FOR UPDATE` on the run row, so audit sequence numbers are gap-free and the chain is linear.
- **Hash chain**: `hash = sha256(prevHash || canonicalJson(event))` with sorted keys so verification survives jsonb key reordering; `GET /v1/claims/{id}/audit` returns events plus a verification result. A database **trigger rejects UPDATE/DELETE** on `audit_events`.
- An in-memory store implements the same port with identical semantics for tests, evals and the offline demo.

## Consequences

- One battle-tested dependency covers state, queueing semantics (leases) and audit; no extra infrastructure.
- Tampering by a DBA is detectable (chain break), though not preventable; anchoring the latest hash per day in WORM storage is on the roadmap.
- Checkpoints duplicate state per step; at claim volumes (thousands/day) this is negligible, and old checkpoints can be partitioned by month.

## Alternatives considered

- **Event store / Kafka**: natural for audit, but adds infrastructure and still needs a state store for resume.
- **Kysely**: equally good; Drizzle chosen for schema-as-code plus migration generation.
- **Ledger databases (QLDB-style)**: strong immutability, limited availability and portability.
