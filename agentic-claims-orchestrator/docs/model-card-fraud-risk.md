| | |
|---|---|
| **Owner** | Claims Analytics (portfolio reference implementation) |
| **Artifact** | [`packages/core/src/ml/fraud-model.v1.json`](../packages/core/src/ml/fraud-model.v1.json) |

| **Serving** | Pure TypeScript scorer [`packages/core/src/ml/fraud-model.ts`](../packages/core/src/ml/fraud-model.ts), in-process, no inference server |
| **Algorithm** | Standardized logistic regression (L2, lbfgs, C=1.0) |
| **Status** | Reference / demo. Trained on synthetic data only. **Not for production decisions without retraining and validation on real, governed data.** |

## Intended use

- Produce a **risk indicator** (probability + band) for incoming first-notice-of-loss (FNOL) claims, used to **route** claims: low risk may go straight through; medium risk goes to an adjuster; high risk (score >= 0.70) goes to the Special Investigations Unit (SIU).
- The score **never denies a claim by itself**. Every adverse path (denial, SIU referral) requires a human decision, enforced by the policy engine (`HITL-DENIAL`, `HITL-SIU-HIGH-FRAUD`).
- The LLM only **explains** the score in plain language from the exact per-feature contributions; it cannot change it.

Out of scope: pricing/underwriting, claimant credit or identity decisions, any automated adverse action.

## Features

All features are derived from the claim, the policy and the claims history. **No protected attributes or close proxies** (age, gender, ethnicity, marital status, postal code, name, language) are used.

| Feature | Definition | Coefficient (standardized) |
|---|---|---|
| `log_claim_amount` | ln(1 + claimed amount USD) | +0.364 |
| `amount_to_limit` | claimed / coverage limit, capped at 3 | +0.474 |
| `policy_tenure_log` | ln(1 + days from policy start to loss) | -0.912 |
| `report_delay_days` | days from loss to notice, capped at 365 | +0.413 |
| `prior_claims_24m` | prior claims on the policy in 24 months (point-in-time), capped at 10 | +0.244 |
| `night_incident` | incident between 00:00 and 04:59 | +0.250 |
| `missing_police_report` | theft/collision/vandalism without police report | +0.476 |
| `documentation_gap` | 1 if no amount document, else \|claimed - documented\| / claimed | +0.675 |

Feature engineering is implemented twice (Python for training, TypeScript for serving) and kept in sync by **parity vectors**: the training script exports 8 test rows with their probabilities and the TS unit test asserts agreement to `1e-9`.

## Training data

Synthetic, generated by `synthesize()` in the training script from a documented generative process (fixed seed `20261017`, 20,000 rows, 6.5% positive rate). The dataset hash is stored in the artifact and CI retrains the model and fails if the coefficients or the data hash drift (`ml` job).

## Evaluation (held-out 25%, synthetic)

| Metric | Value |
|---|---|
| ROC AUC | 0.878 |
| Brier score | 0.046 |
| Precision / recall @ 0.30 (adjuster review) | 0.51 / 0.36, flag rate 4.6% |
| Precision / recall @ 0.70 (SIU) | 0.80 / 0.13, flag rate 1.1% |

The SIU threshold is deliberately conservative (high precision, low flag rate) because SIU capacity is the scarce resource; the 0.30 band widens human review at modest volume.

## Limitations and risks

- **Synthetic data**: metrics demonstrate the pipeline, not real-world performance. Real deployment requires retraining on historical claims with confirmed fraud labels, which are sparse, delayed and biased toward investigated claims (selection bias).
- **Label bias / feedback loops**: claims routed to SIU are more likely to be labelled fraud. Retraining must correct for investigation selection (e.g. inverse propensity weighting or random audit samples).
- **Proxy discrimination**: even without protected attributes, features such as night-time incidents or police reporting can correlate with protected groups. Before production: disparate-impact analysis (e.g. adverse-impact ratio per available segment), and monitoring of review/referral rates by segment.
- **Drift**: monitor feature distributions (PSI) and score distribution per month; alert when the medium/high flag rates move > 50% from baseline.
- **Linear model**: cannot capture interactions; chosen for transparency. A gradient-boosted model can replace it behind the same `FraudModel` interface if it keeps exact per-claim explanations (e.g. TreeSHAP exported alongside).

## Regulatory notes

Designed to support explainability and human-oversight expectations (e.g. EU AI Act human-oversight and record-keeping principles, NAIC model bulletin on the use of AI by insurers, unfair-claims-settlement-practice rules): every score is logged with model version and top factors in the hash-chained audit trail (`fraud.scored` event), and no adverse decision is automated.
