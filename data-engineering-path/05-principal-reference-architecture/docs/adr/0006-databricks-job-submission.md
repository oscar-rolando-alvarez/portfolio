# ADR 0006 · Submit Databricks runs per layer from Airflow, from Git, on policy-bound job clusters

- **Status:** accepted
- **Date:** 2026-11-18

## Options

| Option | Trade-off |
|---|---|
| **`DatabricksSubmitRunOperator` per layer** (chosen) | Each layer is retried, timed out and alerted on independently; a cluster start-up per layer (about 3-5 min, less with pools or serverless) |
| `DatabricksWorkflowTaskGroup` | One Databricks job and a shared job cluster for all layers; faster, but the job definition is generated by Airflow and repair semantics live in Databricks |
| Jobs defined in Databricks Asset Bundles or Terraform, triggered with `DatabricksRunNowOperator` | Job definitions versioned next to the Spark code; Airflow only triggers. Best when a separate team owns the Spark jobs |
| Interactive all-purpose clusters | Fast iteration, but idle cost, shared state and drift. Not for production |

## Decision

Per-layer `DatabricksSubmitRunOperator` with `deferrable=True`, `idempotency_token = hash(dag, task, run_id)`, code from `git_source` pinned to a branch or tag, `new_cluster` constrained by the `jobs` cluster policy (UC access mode, node allowlist, max workers, spot with on-demand driver, cost tags). Moving to `DatabricksWorkflowTaskGroup` is the first optimisation if start-up time exceeds 20% of job time.

## Consequences

- Retries never double-launch clusters, and waiting costs no Airflow worker slots.
- Cluster spend is bounded by policy, not by convention, and every run is attributable by tag.
- Local development uses the `databricks-local` stand-in (Level 4), which implements the same Jobs API subset; contract tests keep it honest.
